## Approval and Versioning
Build -> pending; confirm BOTH plans -> confirmed; separate activate -> one new
in-memory pair version containing both snapshots and their sources. No trainer
step is added to Route B; Route A remains unchanged. A pair is never partially
applied. Failures after preparing either half or just before commit restore all
state, version and audit. This is a local simulation, not durable DB proof.

Limited manual edits select an already declared training day or meal moment.
Frozen validators decide validity; changing either invalidates pair confirmation.
Other editing remains in the accepted source demos; this adapter is not a new
editor for workouts, calories or portions. Changed sources invalidate drafts.
Exact duplicate requests do not create extra versions; altered payload, stale
requests and inappropriate transitions reject. Rejected proposals cannot activate.

Restore version1 after a different version2 requires fresh confirmation and a
separate activation, creating version3. Originals remain immutable. This scope
conservatively refuses restore when source content differs from the old version,
even if some parts might independently fit: prepare a new review instead. It never
silently presents an old instruction as a current one. The original source and
the restored-from version are retained in synthetic audit/history.

Health latches survive source replacement and self-report. No expiry, deletion,
refresh or absence of a recognized signal is medical clearance. The demo's reset
only starts a fresh fictional fixture. Consent withdrawal prevents further
processing/new proposals/activation/replay; prior synthetic history remains.
No generalized subscription/chat/history block is introduced. O5 and D1-D12 remain
unchanged; this package adds no live retention or recognition implementation.
